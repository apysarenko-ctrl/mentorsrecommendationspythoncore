Модуль 1

Вступ до Python

Цей матеріал доповнює перший модуль кількома практичними порадами, які варто взяти в роботу одразу — вони стосуються того, з чим ви щодня матимете справу: змінних, типів даних і форматування виводу.

Рекомендації

1F-рядки замість конкатенації

Використовуйте f-рядки замість конкатенації через + або методу .format(). Порівняйте: "Ціна: " + str(price) + " грн" проти f"Ціна: {price} грн" — другий варіант коротший, читабельніший і дозволяє одразу форматувати число всередині фігурних дужок, наприклад f"{price:.2f} грн" округлить суму до двох знаків після коми. На практиці саме f-рядки — стандарт де-факто в сучасному Python-коді.

2Пастка з дійсними числами

Пам'ятайте про пастку з дійсними числами: вираз 0.2 + 0.1 == 0.3 поверне False, тому що дійсні числа зберігаються в двійковому форматі з обмеженою точністю. Для грошових розрахунків або будь-яких обчислень, де точність критична, варто або порівнювати числа з округленням, або використовувати спеціалізований модуль decimal — про нього детальніше поговоримо в модулі 5, але знати про саму пастку варто вже зараз.

3Зрізи для розвороту й копіювання

Зрізи (slice) — один із найкорисніших інструментів роботи зі списками та рядками. Запис my_list[::-1] розгортає послідовність у зворотному порядку без виклику методу reverse(), а my_list[:] створює поверхневу копію списку, що зручніше й наочніше за виклик .copy().

Типова помилка

Типова помилка початківців — плутати оператор присвоєння = з оператором порівняння ==. Вираз x = 5 записує значення 5 у змінну x, тоді як x == 5 лише перевіряє, чи дорівнює x п'яти, і повертає True або False, нічого не змінюючи. Ця помилка особливо підступна в умовних конструкціях, хоча в Python вона одразу викличе SyntaxError, а не мовчки зіпсує логіку, як у деяких інших мовах.

Корисні джерела

Модуль 2

Контроль потоку та функції

У цьому модулі ви освоюєте умови, цикли та функції — базові інструменти, з якими працюватимете в кожному наступному проєкті. Ось кілька практик, які варто виробити зараз, поки звички ще формуються.

Рекомендації

1enumerate() замість ручного лічильника

Коли у циклі for вам одночасно потрібні й індекс елемента, і сам елемент, не заводьте окрему змінну-лічильник вручну — використовуйте enumerate(). Замість i = 0 / for item in items: ... / i += 1 напишіть просто for i, item in enumerate(items):. Код стає коротшим і менш схильним до помилок на кшталт забутого i += 1.

2Пастка зі змінюваним аргументом за замовчуванням

Один із найвідоміших «підводних каменів» Python — змінюваний аргумент за замовчуванням. Функція def add_item(item, items=[]): виглядає нешкідливо, але порожній список [] створюється лише один раз при визначенні функції, а не при кожному виклику — тож усі виклики без явного items діляться одним і тим самим списком, який накопичує елементи від виклику до виклику. Правильний підхід — значення за замовчуванням None, а сам порожній список створювати вже всередині функції:

def add_item(item, items=None):
    if items is None:
        items = []

3match / case для довгих ланцюжків умов

Якщо ланцюжок if / elif / else стає надто довгим і порівнює одну й ту саму змінну з кількома конкретними значеннями, з Python 3.10 можна замінити його на оператор match / case — він читається природніше, особливо коли варіантів багато.

Типова помилка

Типова помилка з циклом while — забути оновити умову виходу всередині тіла циклу. Якщо while count < 10: не змінює count у кожній ітерації, цикл ніколи не завершиться сам, і програма «зависне» — доводиться перевіряти вручну, чи справді змінна, від якої залежить умова, змінюється на кожному кроці.

Корисні джерела

Модуль 3

Робота з датою, часом та розширена робота з рядками

Дати, час і рядки — теми, у яких найлегше отримати код, що працює «на моєму комп'ютері», але ламається деінде. Кілька порад нижче саме про це.

Рекомендації

1Часові зони явно

Там, де це можливо, працюйте з часовими зонами явно: datetime.now(timezone.utc) замість «наївного» datetime.now() без прив'язки до зони. Наївні дати зручні для навчальних прикладів, але в реальних застосунках, де користувачі можуть бути в різних часових поясах, вони — джерело прихованих багів, які важко відтворити й ще важче знайти.

2math.isclose() для дійсних чисел

Для порівняння дійсних чисел використовуйте math.isclose(a, b), а не оператор ==. Ми вже згадували пастку з 0.1 + 0.2 != 0.3 — math.isclose() дозволяє задати допустиму похибку (параметр rel_tol) і порівнювати числа «достатньо близько», а не побітово точно.

3join() замість += у циклі

Якщо потрібно зібрати рядок із багатьох частин у циклі, не робіть це через += у циклі (result += item) — кожне таке додавання створює новий рядок у пам'яті, бо рядки незмінні. Значно ефективніше зібрати всі частини в список і одним викликом " ".join(parts) отримати результат.

Типова помилка

Типова помилка з регулярними виразами — забути про «сирі» рядки (raw strings). Шаблон "\d+" і r"\d+" можуть на перший погляд виглядати однаково, але без префіксу r звичайний рядок спершу проходить через власне екранування Python, і для складніших шаблонів це призводить до неочікуваної поведінки. Просте правило: для будь-якого регулярного виразу пишіть r"...".

Модуль 4

Робота з файлами та модульна система

Робота з файлами й модулями — та частина курсу, де дрібні звички визначають, наскільки переносимим і стабільним вийде ваш код на різних машинах і операційних системах.

Рекомендації

1Явний encoding='utf-8'

Завжди явно вказуйте encoding='utf-8' при відкритті файлів: open("data.txt", "r", encoding="utf-8"). Без цього параметра Python використовує кодування за замовчуванням операційної системи — а на Windows це часто CP1251, тоді як файл міг бути збережений у UTF-8. Результат — або UnicodeDecodeError, або мовчазне псування кирилиці, і те й інше складно діагностувати, якщо не знати, з чого починати.

2pathlib замість рядкових шляхів

Для роботи зі шляхами обирайте pathlib замість рядкового конкатенування чи навіть модуля os.path. Запис Path("data") / "reports" / "file.txt" автоматично використовує правильний роздільник шляху для поточної операційної системи: у Windows це \, а в Linux і macOS — /. Натомість під час склеювання шляхів вручну через + потрібно самостійно враховувати ці відмінності, що легко може призвести до помилок.

3requirements.txt як звичка

Виробіть звичку фіксувати залежності проєкту: спочатку активуйте віртуальне оточення проєкту, встановіть необхідні пакети, а потім виконайте pip freeze > requirements.txt. Після цього перевірте файл і переконайтеся, що в ньому немає зайвих пакетів. Якщо виконати pip freeze поза віртуальним оточенням, у requirements.txt можуть потрапити пакети з глобального середовища, які проєкту не потрібні.

Типова помилка

Типова помилка — назвати власний файл так само, як модуль стандартної бібліотеки, наприклад random.py у корені проєкту. Python шукає модулі спершу в поточній робочій директорії, тож import random підхопить саме ваш файл замість вбудованого модуля — і код впаде з незрозумілою помилкою, доки ви не здогадаєтесь перейменувати власний файл.

Корисні джерела

Розділ офіційної документації Python про pathlib — там є повний перелік методів для роботи зі шляхами, директоріями та метаданими файлів.

Модуль 5

Функціональне програмування та вбудовані модулі Python

Стандартна бібліотека Python приховує чимало готових рішень для задач, які інакше довелося б писати вручну. У цьому модулі варто звернути увагу саме на них.

Рекомендації

1collections.Counter для підрахунку

Для підрахунку частоти елементів (літер у рядку, слів у тексті, будь-яких гешованих значень у списку) не пишіть цикл із ручним словником-лічильником — використовуйте collections.Counter. Counter("banana") одразу дає словникоподібний об'єкт із кількістю кожного символу, а метод most_common() відсортує результат за спаданням частоти без додаткового коду.

2Comprehensions

List comprehensions ([x**2 for x in range(10) if x % 2 == 0]) справді компактніші за еквівалентний цикл for з append(), але в них легко перестаратися. Якщо вираз усередині comprehension вже не влазить в один погляд ока — краще повернутися до звичайного циклу: читабельність коду важливіша за його стислість.

Типова помилка

Типова помилка при написанні власних декораторів — забути functools.wraps. Без нього декорована функція «втрачає» власне ім'я та рядок документації (обидва підміняються на ім'я й документацію внутрішньої функції-обгортки), що потім заплутує і автодоповнення в редакторі, і будь-який код, який звертається до __name__ функції.

Корисні джерела

Офіційна документація модуля functools — там детально описані і lru_cache, і wraps, і інші декоратори стандартної бібліотеки, які варто знати, перш ніж писати власні.

Модуль 6

Основи роботи з класами

Перші класи мають допомогти зрозуміти, як об’єднувати дані та поведінку, а не перетворитися на набір складних конструкцій.

Рекомендації

1Починайте з простого питання: «Що є об’єктом?»

Перед створенням класу сформулюйте, що саме ви хочете описати.

2Не робіть клас просто «контейнером для всього»

Поганий початок:

class User:
    name = …
    age = …
    address = …
    orders = …
    settings = …
    ...

Клас не повинен автоматично ставати місцем, куди складають усі дані, пов’язані з певною сутністю.

Краще подумати про відповідальність класу: що саме він представляє і за що відповідає.

3Звикайте до __init__ та self

Це одна з перших речей, яку варто добре зрозуміти:

class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

self.name і self.email — це дані конкретного екземпляра класу.

Наприклад:

user1 = User("Anna", "anna@example.com")
user2 = User("Oleh", "oleh@example.com")

user1 і user2 мають власні значення name та email.

4Не бійтеся створювати маленькі класи

Перший клас зовсім не повинен бути великим.

Наприклад:

class BankAccount:
    def __init__(self, balance):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

Цього вже достатньо, щоб потренувати:

  • створення класу;
  • __init__;
  • self;
  • атрибути;
  • методи;
  • створення екземплярів;
  • зміну стану об’єкта.

5Методи мають працювати з даними самого об’єкта

Якщо клас представляє банківський рахунок, логічно, щоб він сам умів поповнювати баланс:

account.deposit(100)

а не щоб зовнішній код постійно змінював його напряму:

account.balance += 100

Це поступово підводить до важливої ідеї ООП: об’єкт об’єднує стан і операції над цим станом.

6Навчіться розрізняти клас та екземпляр

Це фундаментальна річ.

class Dog:
    def __init__(self, name):
        self.name = name

Dog — клас, своєрідний опис того, яким буде об’єкт.

dog = Dog("Buddy")

dog — екземпляр класу, конкретний об’єкт.

Корисно постійно ставити собі питання: «Я зараз працюю з описом типу чи з конкретним об’єктом?»

Типова помилка

Типова помилка — використати змінюваний тип (список, словник) як атрибут класу, очікуючи, що кожен об'єкт отримає власну копію. Якщо оголосити список на рівні класу, а не всередині __init__, він стане спільним для всіх екземплярів — додавання елемента в один об'єкт «магічним чином» з'явиться і в усіх інших, бо це фактично один і той самий список у пам'яті.

Модуль 7

Розширене об'єктно-орієнтоване програмування в Python

ООП — це не лише синтаксис класів, а й ціла культура написання коду, яка одразу відчувається у зрілих Python-проєктах. Кілька практик нижче допоможуть писати класи, що виглядають «по-python'івськи» з перших спроб.

Рекомендації

1Реалізовуйте __repr__

Краще реалізовуйте __repr__ для власних класів, навіть якщо у вас уже є __str__. __str__ призначений для читабельного виводу (наприклад, у print()), а __repr__ — для однозначного, «технічного» представлення, яке бачите в консолі під час налагодження чи в логах. Якщо __str__ немає, Python автоматично використає __repr__ як запасний варіант — а от навпаки це не працює.

2@classmethod як альтернативний конструктор

Використовуйте @classmethod для альтернативних конструкторів, коли потрібно створювати об'єкт не з окремих аргументів, а, наприклад, із рядка. Класичний приклад —

Employee.from_string("Ivan;Developer;50000")

який усередині розбирає рядок і повертає готовий екземпляр cls(...) — це чистіше, ніж перевантажувати сам __init__ логікою парсингу різних форматів вхідних даних.

3@dataclass для класів-сховищ даних

Якщо клас потрібен переважно для зберігання даних (а не для складної логіки), не пишіть __init__ вручну для кожного поля — скористайтеся декоратором @dataclass з модуля dataclasses. Він сам згенерує конструктор, __repr__ та деякі інші магічні методи за оголошеними полями класу, і код стане в рази коротшим.

4Стиль EAFP замість зайвих перевірок типу

Python традиційно тяжіє до стилю EAFP («Easier to Ask Forgiveness than Permission») — простіше спробувати виконати дію і обробити виняток, ніж заздалегідь перевіряти всі умови. Замість перевірки isinstance(obj, SomeClass) перед викликом методу часто природніше просто викликати потрібний метод і обробити AttributeError, якщо його не існує — саме на цьому й тримається качина типізація.

5Enum замість «магічних» рядків і чисел

Для набору іменованих констант (статуси замовлення, дні тижня, ролі користувачів) використовуйте Enum замість рядків чи чисел «навмання». Статус order.status == OrderStatus.SHIPPED читається набагато зрозуміліше й надійніше за order.status == "shipped", де легко помилитися в написанні рядка, і жоден інструмент про це не попередить.

Типова помилка

Типова помилка при перевизначенні операторів порівняння (__eq__, __lt__ тощо) — повертати False, коли метод не знає, як порівняти об'єкт з іншим типом даних. Правильна поведінка — повернути спеціальне значення NotImplemented: тоді Python спробує звернутися до відповідного методу другого об'єкта, і лише якщо жоден спосіб не спрацював, згенерує TypeError.

Серіалізація та копіювання об'єктів в Python

Останній модуль блоку Python Core — про те, як дані «виживають» після завершення програми та як безпечно копіювати складні об'єкти. Кілька практичних рекомендацій на цю тему.

Рекомендації

1json замість pickle для недовірених даних

Коли є вибір, віддавайте перевагу json перед pickle — особливо якщо серіалізовані дані можуть потрапити ззовні (від користувача, з мережі, зі стороннього джерела). pickle виконує довільний код при десеріалізації, тому розпаковування pickle-даних з недовіреного джерела — це вразливість, тоді як json обмежений простими типами даних і не виконує код за визначенням. pickle варто лишати для внутрішніх задач, де ви самі і серіалізуєте, і десеріалізуєте дані.

2ensure_ascii=False та indent=4 для JSON

Якщо серіалізуєте текст із кирилицею в JSON, одразу додавайте параметри ensure_ascii=False (щоб символи зберігалися як є, а не як unicode escape-послідовності) та indent=4 (щоб файл лишався читабельним для людини, а не одним суцільним рядком). Це особливо корисно, коли JSON-файл доводиться відкривати й перевіряти вручну під час налагодження.

3csv.DictReader / DictWriter за іменами колонок

Для роботи з CSV-файлами, де є рядок заголовків, використовуйте csv.DictReader і csv.DictWriter замість звичайних csv.reader / csv.writer. Тоді до значень можна звертатися за іменами колонок (row["name"]) замість числових індексів (row[0]) — код стає стійкішим до змін порядку колонок у файлі й одразу зрозумілішим для того, хто читає код пізніше.

Типова помилка

Типова помилка при роботі з CSV на Windows — забути параметр newline="" при відкритті файлу: open("data.csv", newline=""). Без нього модуль csv може додавати зайві порожні рядки між записами через те, як по-різному Windows і сам модуль csv обробляють символи закінчення рядка. Ця помилка на Linux чи macOS взагалі не відтворюється, тому важливо знати про неї заздалегідь.
